Scoping written on 2026-11-11 from `main` at `f044143`, on the real code.

## 1. Findings on the existing code

- An operation is a plain JSON object, validated by `parseOperation`, anchored on a `baseHash`
  (§7 bis of the plan). `apply(document, op)` in `adapter-gitlab` returns the new text, its hash and
  a new `document` re-read with its `include`s: a sequence can therefore be chained without
  re-reading the disk.
- No command applies an operation outside the server. The plan announces it (`keelson apply
  ops.json`, §8) without settling its shape.
- The CLI already depends on `@keelson/server` (for `start`): its atomic write `writeAtomic` and its
  bounded variant `writeInsideRoot` can be reused without a new dependency.
- The preview's line-by-line diff lives in `packages/ui/src/editing/diff.ts`, hence out of reach of
  the CLI, which does not depend on the UI.

## 2. Decisions

- **D1 — shape.** `keelson apply <ops.json> [<repo>...] [--file <path>] [--rebase] [--dry-run]
  [--json]`. Without a repository, the current folder. The target file defaults to
  `.gitlab-ci.yml`, relative to each repository's root.
- **D2 — operations file.** A single operation or a JSON array of operations, each validated by
  `parseOperation` before touching any repository. Unreadable JSON, empty array or invalid
  operation: exit **2**, message rendered by `@keelson/core/messages`, which names the faulty index
  (`operations[1]: …`).
- **D3 — sequence.** Operations are applied in order, each on the result of the previous one, in
  memory. The file is written **once**, atomically, and only if the whole sequence succeeds: all or
  nothing per repository.
- **D4 — fleet.** Each repository is processed independently: the failure of one does not stop the
  others. Exit **1** if at least one repository fails, **0** otherwise.
- **D5 — `--rebase`.** The `baseHash` of each operation is replaced by the hash of the current text
  at that step. This is what makes the same operations file applicable to N repositories whose
  texts differ. Without `--rebase`, a `baseHash` that does not match returns `STALE_DOCUMENT` for
  that repository, without writing anything.
- **D6 — `--dry-run`.** Everything is computed, nothing is written. Each successful repository
  shows its number of added and removed lines, the hash of the new text and a unified diff without
  context (`-U0`).
- **D7 — boundary.** The target file is read by `readInsideRoot` and written by `writeInsideRoot`:
  a path, or a link, that leaves the repository root is refused without reading or writing.
  `include`s are read by `createFileReader`, bounded to the same root.
- **D8 — output.** One line per repository, in argument order, on standard output:
  `✓ <repo>  <n> operation(s) applied` or `✗ <repo>  <rendered error>`. An operation error names
  its index and its kind: `operations[2] (removeJob): job "x" does not exist in this file`.
- **D9 — `--json`.** `{ "results": [{ "repo", "ok", "applied", "written", "hash"?, "error"? }] }`.
  `error` carries `message`, and for an operation error `operation` (the index), `kind`, `code` and
  `params`: as for `validate`, the `params` are the contract, the message is for humans.

## 3. Out of scope

- Producing the operations: they come from the UI, a script or a human. No generator.
- `adapter-github`: `apply` only targets GitLab CI, like the server.
- Toolchain operations (`.devsecops/toolchain.yaml`).
- Cloning, committing or pushing the repositories: `apply` writes a file, versioning is left to the
  caller.
