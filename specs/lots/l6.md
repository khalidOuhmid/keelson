# Lot L6 — adaptateur GitHub Actions

Cadrage écrit le 2026-11-11 depuis `f044143`, sur le code réel.

## 1. Constats sur l'existant

- `packages/adapter-github` n'exportait que `PACKAGE_NAME`. Le serveur, la CLI et l'UI ne
  connaissaient qu'un fichier, `.gitlab-ci.yml`, et `AdapterName` valait `"gitlab"`.
- L'IR (`Pipeline`, `Job`, `Stage`) est neutre vis-à-vis du fournisseur, sauf `stage` : GitHub
  Actions n'a pas de stages.
- La détection des couches lit l'image et les lignes de script. Un workflow GitHub délègue l'essentiel
  à des actions (`uses: aquasecurity/trivy-action@…`) qu'aucun motif de script ne voit.
- Le catalogue porte déjà un snippet `github` par fiche (liste de steps).

## 2. Décisions

- **D1 — lecture d'abord.** L6 lit les workflows et en calcule la couverture. L'édition d'un
  workflow est refusée par un code public, `READ_ONLY_ADAPTER` `{ adapter, file }`, en 422, pour
  les opérations comme pour la prévisualisation, sans rien écrire. L'édition est un écart daté.
- **D2 — détection de l'espace de travail.** `.gitlab-ci.yml` d'abord, puis
  `.github/workflows/*.yml|yaml` de premier niveau, triés, chacun passé par le lecteur qui tient la
  frontière de la racine.
- **D3 — niveaux plutôt que stages.** Le stage d'un job est `level N`, N étant la longueur de la
  plus longue chaîne de `needs` qui y mène, comme le graphe de GitHub. Les stages sont implicites,
  sans plage, d'origine `default`. Un cycle ou un need inconnu ne fait pas monter le niveau :
  `validate` les signale (`NEEDS_CYCLE`, `UNKNOWN_NEED`), la mise en page ne boucle pas.
- **D4 — signaux.** `script` met bout à bout les lignes non vides des `run` ; `image` vient de
  `container` (chaîne ou `container.image`) ; un nouveau champ optionnel `JobSignals.actions` porte
  chaque `uses` sans sa version, step ou workflow réutilisable. Absent côté GitLab : les goldens ne
  bougent pas.
- **D5 — catalogue.** `detect.actions` optionnel : `owner/repo` et ses sous-chemins
  (`github/codeql-action/init`), sans casse, jamais un dépôt au nom voisin. Une action de service
  prouve aussi l'intégration, contrairement à une image.
- **D6 — opaque.** Tout ce que l'IR ne modélise pas reste un bloc opaque à sa plage exacte :
  `runs-on`, `steps`, `strategy`… au niveau du job, `name`, `on`, `permissions`… au niveau racine.
- **D7 — UI.** Un sélecteur « CI file » apparaît dès qu'il y a plus d'un fichier ; un workflow
  ouvert porte l'étiquette « GitHub Actions · read-only » et tous les contrôles d'édition sont
  désactivés par `canEdit()`.
- **D8 — CLI.** `validate` et `coverage` choisissent l'adaptateur par le chemin ; sans `.git`, la
  racine d'un workflow est le dossier qui porte `.github`.
